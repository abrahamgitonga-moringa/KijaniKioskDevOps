Reflection Questions
Q1: What specific information did kubectl describe pod show that kubectl get pods could not, and what did that information tell you that you could not have known from the STATUS column alone?

While kubectl get pods -l app=kk-payments provides an operational summary displaying high-level statuses like ImagePullBackOff, CrashLoopBackOff, or OOMKilled, it abstracts away the specific cause of failure. Executing kubectl describe pod exposes the granular Events timeline at the bottom of the output, exact container State/Last State fields (e.g., Exit Code: 137), and explicit error strings such as manifest unknown or missing resource capacity. This structural detail revealed the exact reason why a Pod was failing—such as an unauthenticated/non-existent image tag or memory allocation exhaustion—which is impossible to determine from the high-level STATUS column alone.

Q2: Describe the exact difference in the experience of creating nginx-imperative vs nginx-declarative. Focus on what happened after deletion: what would you need to recreate each resource? Which approach leaves you in a better position and why?

Creating nginx-imperative imperatively via kubectl create deployment executed directly against the API server without leaving a local trace, whereas nginx-declarative was generated with --dry-run=client -o yaml, updated to include the week: "9" metadata label, and applied declaratively. Once both resources were deleted using kubectl delete, recreating nginx-imperative required remembering and re-typing the exact CLI flags from memory or shell history, creating significant room for human error and configuration drift. In contrast, nginx-declarative can be instantly and identically recreated at any time by executing kubectl apply -f nginx-declarative.yaml. The declarative approach leaves you in a far superior position because it provides version-controlled Infrastructure as Code, ensuring reproducible deployments, seamless peer code review, and automated CI/CD pipeline integration.

Q3: In the CrashLoopBackOff exercise, what did kubectl logs --previous show and what did kubectl logs without --previous return? Why does this matter in a production incident at 02:00 when the container is crashing every 30 seconds?

Executing kubectl logs without flags returned output from the currently restarted, active container instance, which was often empty or limited to initial startup output before the process crashed again. Running kubectl logs --previous explicitly retrieved the stdout/stderr streams from the immediately preceding container instance right before it crashed. In a 02:00 production incident where a container is rapidly cycling in a CrashLoopBackOff state every 30 seconds, standard kubectl logs routinely returns blank outputs because the application crashes before writing to the new container's log buffer. Utilizing --previous ensures engineers immediately capture the fatal exception or missing configuration error (such as ERROR: DATABASE_URL not set) from the failed run without racing against Kubelet's restart loop.

Q4: The Week 4 Ansible playbook is idempotent: running it twice with no changes produces no unexpected effects. Describe what the output was when you applied the nginx-declarative manifest a second time with no changes. What does idempotency mean in the context of a CI/CD pipeline that applies manifests on every merge?

When applying nginx-declarative.yaml a second time without making any modifications, the terminal returned deployment.apps/nginx-declarative unchanged instead of created or configured. In the context of a CI/CD pipeline that applies manifests on every merge, idempotency guarantees that re-applying declarative manifests safely converges the cluster toward the desired state without causing unnecessary disruptions. If no underlying specifications (e.g., image tags, resource limits, labels) have changed, Kubernetes leaves running Pods untouched and avoids unnecessary rolling restarts, ensuring system stability while enforcing declared state consistency.
